# MetroMate

**2026 捷運盃黑客松「玩點生活・智慧串聯」創新應用競賽提案作品**

MetroMate 是以台北捷運 Go App 與捷運點生態系為基礎所發想的智慧生活推薦平台。

專案並非取代既有的路線規劃與乘車資訊，而是希望在現有服務上加入 AI 情境推薦、捷運點使用引導、遊戲化任務與合作商家機制，讓使用者能依照所在位置、時間、預算、偏好與點數狀態，取得更符合當下需求的捷運生活圈建議。

---

## 專案動機

目前捷運點生態系仍面臨幾項問題：

* 累點管道較集中，缺乏穩定的日常累積機制
* 使用者對捷運點的使用方式與價值認知不足
* 點數可能因累積不足或即將到期而未被有效使用
* 中小型商家參與行銷合作時，需承擔較高的前期成本
* 使用者規劃聚餐、約會或休閒行程時，常需要在不同平台之間切換資訊

因此，我們希望透過 MetroMate 串聯使用者、合作商家與台北捷運，讓捷運點更容易取得、使用與流通。

## 核心功能

### AI 情境推薦

使用者可以直接以自然語言描述需求，例如：

* 甜點、鮮花、野餐
* 古蹟、咖啡、散步
* 親子、展覽、下午茶

系統會解析使用者的活動類型、地區、預算、時間與偏好，再從符合條件的地點中提供建議。

### 智慧路線推薦

推薦結果不只考慮景點本身，也會納入：

* 偏好符合度
* 路線順暢度
* 預算
* 營業時間
* 步行與轉乘成本
* 捷運點累積與折抵
* 即將到期點數的使用機會

概念上的推薦分數為：

`偏好符合度 + 路線順暢度 + 點數誘因 + 預算符合度 + 到期點數可用性 − 移動成本`

### 捷運點使用引導

MetroMate 可協助使用者了解：

* 哪裡可以累積捷運點
* 哪些合作商家可以使用點數
* 哪些點數即將到期
* 哪些路線同時具有累點或折抵機會

### 遊戲化任務

透過 LBS 與城市探索任務增加捷運點的累積場景，例如：

* 捷運站探索任務
* 合作商家到店任務
* 離峰搭乘加碼
* GPS 打卡
* YouBike 轉乘回饋

## 系統架構

MetroMate 採用「規則引擎 + AI」的混合架構。

AI 主要負責理解使用者需求與產生推薦文字，而涉及實際規則與交易的部分，例如路線排序、點數計算、任務資格與核銷驗證，則交由後端與資料庫處理，以降低 AI 幻覺或錯誤判斷對實際服務造成影響。

### 使用者互動層

* React
* Vite
* Leaflet
* PWA

負責自然語言輸入、地圖與路線呈現、商家資訊及點數提醒。

### AI 推薦層

* Azure OpenAI
* GPT-4o-mini
* Structured Outputs

負責解析使用者的活動類型、地區、預算、時間與偏好。

### 後端規則層

* FastAPI
* Python
* Rule Engine
* Recommendation Ranking Model

負責候選地點查詢、推薦排序、營業時間判斷、點數折抵資格與任務規則。

### 資料與快取層

* PostgreSQL
* PostGIS
* Redis

負責站點、商家、任務、點數與活動紀錄，以及地理位置查詢與熱門資料快取。

## 交易安全與 AI 風險控管

由於捷運點具有虛擬資產的性質，因此專案中特別考慮交易一致性與 AI 權限問題。

主要設計包括：

* Idempotency Key，避免重複交易
* Database Transaction 與 Row-level Lock，確保點數異動一致
* Dynamic QR Code 與 HMAC 簽章，降低重複核銷風險
* Timestamp 與 Redis Nonce 驗證
* AI 僅能從資料庫提供的候選清單中產生推薦
* LLM 不具有直接修改點數或交易資料的權限

## MVP 導入規劃

專案規劃採分階段方式導入。

第一階段先以：

* 5–8 個捷運站
* 模擬會員資料
* 少量示範合作商家

建立 MVP，優先驗證 AI 路線推薦、點數到期提醒、離峰加碼與 QR 核銷流程。

待核心流程穩定後，再逐步串接正式 Go App 會員與捷運點資料，降低一次整合既有系統的導入風險。

## 專案心得

MetroMate 最後並未進入決賽，但這次專案對我而言仍是一段很重要的學習經驗。

這次與新的團隊成員合作，讓我接觸到許多與過去不同的觀點。相較於之前的專案，我們不只是討論這個功能看起來好不好，而是花更多時間思考這個功能實際上能不能做、資料從哪裡來、AI 可以負責到什麼程度，以及服務真正導入之後可能會遇到哪些問題。

例如，在設計 AI 推薦功能時，我們進一步思考如何避免 AI 直接影響實際的點數交易，因此將需求理解與推薦文字交給 AI，而點數計算、資格判斷與交易則由後端規則處理。另外也考慮到重複核銷、交易一致性、QR Code 驗證，以及如何先從小規模 MVP 開始測試，而不是一次整合完整系統。

擔任隊長的過程中，我也學到如何整合不同背景成員的意見，並在創意、技術、商業與實際可行性之間找到平衡。

這次經驗讓我更深刻理解，一個完整的專案不只是提出一個有趣的想法，更需要持續思考它是否能被實作、驗證、營運與擴充。
